On the Limits of Small Language Models in Vectorized Code Synthesis

Created on April 18, 2026

“Can small language models reliably synthesize deterministic, high-throughput code without falling into the Python Loop Tax?”

1. Introduction & Theoretical Motivation

Code synthesis for high-throughput data processing represents a fundamentally different challenge from general software engineering. In general code generation benchmarks (e.g. HumanEval, MBPP), models produce procedural code where control flow loops (for, while) and list comprehensions are standard paradigms. However, in data engineering and synthetic data generation, procedural Python loops incur severe interpreter overhead—the Python Loop Tax—slowing execution by orders of magnitude compared to compiled C/C++ or SIMD tensor operations.

Procedural Row Iteration (O(N) Interpreter Overhead):
for i in range(num_rows):
    row = generate_row()   ──► 1,000,000 Python frame evaluations (~15-60s)

Vectorized Array Execution (SIMD / AVX2 Tensor Math):
np.random.choice(categories, p=weights, size=num_rows)  ──► Continuous C-memory buffer (<10ms)

To eliminate this bottleneck, we formulated Gnoril as a neural compiler: fine-tuning compact language models ($0.5\text{B} \rightarrow 7\text{B}$ parameters) to directly translate unstructured natural language dataset requirements into 100% vectorized, zero-loop NumPy and Pandas computation graphs.

This paper investigates three fundamental questions:

  1. Parameter Efficiency: Can sub-billion parameter models (0.5B, 1.5B) reliably learn strict, domain-specific Abstract Syntax Tree (AST) grammar constraints?
  2. The Execution Gap: Why does syntactically compliant vectorized code fail to execute in runtime sandboxes?
  3. Alignment Strategy: How can compiler-in-the-loop feedback mechanisms (such as Direct Preference Optimization) close the execution reliability gap without increasing model parameter scale?

2. Formal AST Invariants & Verification Pipeline

To evaluate code synthesis beyond superficial keyword matching, we established a deterministic static analysis boundary. Synthesized Python programs must satisfy a formal grammar $G_{\text{vec}}$ verified via Python’s ast (Abstract Syntax Tree) module before reaching runtime execution:

2.1 The Three Formal Invariants

\[\text{Invariant 1 (Loop Elimination): } \forall v \in \text{AST}, \text{Type}(v) \notin \{\text{For}, \text{While}, \text{ListComp}, \text{DictComp}, \text{GeneratorExp}, \text{SetComp}\}\]

Dynamic row-level iteration is strictly prohibited. The only permissible iteration is static schema meta-iteration (e.g. iterating over a fixed compile-time tuple of column definitions).

\[\text{Invariant 2 (Banned Iterative Methods): } \forall a \in \text{AST.Attribute}, \text{attr}(a) \notin \{\text{'apply'}, \text{'iterrows'}, \text{'itertuples'}, \text{'applymap'}, \text{'transform'}\}\] \[\text{Invariant 3 (Tensor Primitive Mapping): } \text{Logic}(x) \rightarrow \{\text{np.where}, \text{np.select}, \text{np.random.choice}, \text{np.random.normal}, \text{pd.to_datetime}\}\]

Conditional branching must be mapped to vector multiplexers (np.where for binary conditions, np.select for multi-case logic) rather than Python if/else statements evaluated per row.

3. Empirical Evaluation: The “Syntax vs. Semantics” Execution Gap

We evaluated four fine-tuned model variants built upon the Qwen2.5-Coder backbone across 15 complex dataset specifications in the Gnoril-Bench v1.0 test suite, encompassing high-cardinality categoricals, temporal offsets, skewed numerical distributions, and multi-table relational schemas with foreign key dependencies.

The evaluation reveals a sharp conceptual division between two distinct execution layers:

  • Layer 1: Structural Syntax (Static AST Grammar): Models easily acquire anti-loop invariants via SFT ($V\text{-Score} = 60.0\% - 73.3\%$). The model weights successfully learn that procedural for and while constructs are forbidden in the target domain.
  • Layer 2: Runtime Semantics (Dynamic Execution Sandbox): Despite producing structurally compliant code, execution yield ($E\text{-Score}$) collapses ($0.0\% - 13.3\%$) across all scales due to low-level NumPy type contracts, array shape broadcasting, and floating-point normalization errors.

Two primary metrics quantify the model capabilities:

  • Vectorization Score ($V\text{-Score}$): Percentage of generations satisfying all static AST invariants with zero loop nodes.
  • Sandbox Execution Yield ($E\text{-Score}$): Percentage of generations executing to completion in the isolated sandbox, returning a valid, non-empty pd.DataFrame matching schema contracts.

4. In-Depth Taxonomy of Vectorized Code Failures

Analyzing the 60 total generation logs captured by the sandbox worker revealed that execution failures are not random; they follow five specific, deterministic failure signatures:

4.1 Bug Signature 1: Floating-Point Entropy (36.7% of Failures)

  • Symptom: ValueError: probabilities do not sum to 1
  • Root Cause: When asked to generate categorical probabilities (e.g. $[0.6, 0.25, 0.2]$), language models perform approximate token prediction rather than exact floating-point arithmetic. The sum equals $1.05$, causing NumPy’s C-level probability validation check in np.random.choice to reject the array.
  • Code Difference: ```python

    ❌ Faulty Generation (Model hallucinated exact sum):

    p = [0.6, 0.25, 0.2] categories = np.random.choice([‘A’, ‘B’, ‘C’], size=num_rows, p=p)

✅ Defensive Vectorized Pattern (Normalized):

p = np.array([0.6, 0.25, 0.2]) p = p / p.sum() categories = np.random.choice([‘A’, ‘B’, ‘C’], size=num_rows, p=p)


### 4.2 Bug Signature 2: Return Type Contract Violations (23.3% of Failures)
* **Symptom**: `AssertionError: Output must be a pd.DataFrame or dict of DataFrames`
* **Root Cause**: The model synthesizes all columns as raw NumPy arrays (`ids`, `timestamps`, `amounts`), but forgets to encapsulate them into a `pd.DataFrame({...})` or returns a bare NumPy array / dictionary.

### 4.3 Bug Signature 3: Matrix Shape Broadcasting Mismatch (18.3% of Failures)
* **Symptom**: `ValueError: operands could not be broadcast together with shapes (1000,) (1000,1)`
* **Root Cause**: When performing element-wise arithmetic, small models inadvertently introduce extra dimensions (e.g., calling `.reshape(-1, 1)` or `np.expand_dims`), breaking downstream 1D vector operations.

### 4.4 Bug Signature 4: Relational Key Inconsistency (13.3% of Failures)
* **Symptom**: `KeyError: 'user_id' not found in parent table`
* **Root Cause**: In multi-table prompts (e.g. `Users` $\rightarrow$ `Orders`), the model names the primary key in Table 1 `account_id`, but samples foreign keys in Table 2 referencing `user_id`.

### 4.5 Bug Signature 5: Implicit Type Casting Failure (8.3% of Failures)
* **Symptom**: `TypeError: np.char.add() requires strings or bytes-like objects`
* **Root Cause**: The model attempts string concatenation on integer sequence IDs without casting to strings first:
```python
# ❌ Faulty:
ids = np.char.add("ORD_", np.arange(num_rows)) # Crashes (int64 not string)

# ✅ Correct:
ids = np.char.add("ORD_", np.arange(num_rows).astype(str))

5. Why Sub-3B Zero-Shot Self-Correction Fails

In our benchmark suite, whenever a runtime exception was raised, the execution sandbox trimmed the stack trace to the last 4 lines and prompted the model for an in-context surgical repair:

\[\text{Prompt}_{\text{repair}} = \text{Code}_{\text{faulty}} + \text{Traceback} + \text{"Fix line } L \text{ without using loops."}\]
  • Finding: While frontier models ($70\text{B}+$) routinely resolve such syntax bugs via chain-of-thought debugging, sub-3B models rarely succeed in zero-shot multi-turn self-correction.
  • Reason: Small parameter models suffer from attention distraction when presented with multi-line Python tracebacks. In attempting to fix line 14, they frequently introduce regressions in line 4 (e.g. altering variable names or re-introducing procedural loops).

6. The Solution: Execution-Feedback DPO

Because the execution sandbox provides an automated, deterministic reward signal ($\text{Pass} = 1$, $\text{Fail} = 0$), we can eliminate human labeling entirely and construct Direct Preference Optimization (DPO) datasets automatically.

6.1 Mathematical Formulation of Execution DPO

Standard Supervised Fine-Tuning (SFT) only maximizes the log-likelihood of target tokens:

\[\mathcal{L}_{\text{SFT}}(\theta) = -\mathbb{E}_{(x, y) \sim \mathcal{D}} \left[ \sum_{t=1}^{|y|} \log \pi_\theta(y_t | x, y_{<t}) \right]\]

SFT does not actively penalize subtle API mistakes. In contrast, Execution-Feedback DPO directly updates the policy $\pi_\theta$ relative to a reference model $\pi_{\text{ref}}$ by maximizing the margin between the verified working code $y_w$ and the runtime-failing code $y_l$:

\[\mathcal{L}_{\text{DPO}}(\theta; \pi_{\text{ref}}) = -\mathbb{E}_{(x, y_w, y_l) \sim \mathcal{D}_{\text{sandbox}}} \left[ \log \sigma \left( \beta \log \frac{\pi_\theta(y_w | x)}{\pi_{\text{ref}}(y_w | x)} - \beta \log \frac{\pi_\theta(y_l | x)}{\pi_{\text{ref}}(y_l | x)} \right) \right]\]

By training on compiler-harvested $(x, y_w, y_l)$ triplets, the model’s logits for un-normalized probabilities and implicit type errors are suppressed directly in the attention weight matrix.

7. Key Findings & Conclusion

  1. AST Grammar Rules Are Parameter-Efficient: Fine-tuning on fewer than 1,500 samples is sufficient for a 490M parameter model to eliminate procedural loops and acquire vectorized syntax structures ($V\text{-Score} > 66\%$).
  2. Parameter Scaling Alone Does Not Resolve Numerical Alignment: Scaling from 0.5B to 7B parameters does not bridge the Execution Gap; both small and medium models fail on the exact same floating-point summation and array shape contracts.
  3. Execution-Guided Optimization is Essential: Closing the Execution Gap in compact models requires replacing passive token imitation (SFT) with contrastive execution alignment (DPO / RLVR).
